# History Timeline API

Интерактивная платформа для визуализации и анализа исторических процессов, предоставляющая REST API с поддержкой иерархических связей событий, хронологической фильтрации диапазонов, строгим контролем целостности данных на уровне СУБД и математическим ядром временной шкалы на базе пролептического григорианского календаря. Параметр календарной системы заложен в модуль calendar.js как точка архитектурного расширения (в настоящее время поддерживается исключительно единая пролептическая григорианская система).

### Спецификация REST API

#### 1. Интервальная выборка событий (`GET /api/v1/events/range`)

Эндпоинт предназначен для высокопроизводительной интервальной выборки исторических событий, пересекающих заданный хронологический диапазон. Публичная выдача строго ограничена проверенным и подтвержденным контентом со статусом модерации `status = 'approved'`.

##### Параметры запроса (Query Parameters)

| Параметр | Тип данных | Обязательный | По умолчанию | Описание и валидационные ограничения |
| --- | --- | --- | --- | --- |
| `from_date` | `integer (BIGINT)` | Да | — | Начальная хронологическая граница диапазона в секундах Unix. Должна быть `<= to_date`. |
| `to_date` | `integer (BIGINT)` | Да | — | Конечная хронологическая граница диапазона в секундах Unix. Должна быть `>= from_date`. |
| `categories` | `list[string]` | Нет | `None` | Фильтр по категориям: `culture`, `politics`, `economy`, `science`. |
| `ranks` | `list[string]` | Нет | `None` | Фильтр по уровням детализации: `century`, `decade`, `year`, `month`, `day`, `hour`, `minute`, `second`. |
| `skip` | `integer` | Нет | `0` | Смещение пагинации (`ge = 0`). |
| `limit` | `integer` | Нет | `500` | Максимальный размер выборки (`ge = 1`, `le = 5000`). |

##### Схема ответа и четырехуровневая сортировка

Возвращаемая Pydantic-модель: `EventRangeResponse`. Содержит свойства `items` (массив сериализованных событий `EventResponse`), `from_date`, `to_date`, `total` и признак усечения выборки `is_truncated`.

Выдача упорядочивается непосредственно на уровне PostgreSQL по строгому четырехуровневому детерминированному правилу:

1. Глубина ранга детализации `depth_level` по возрастанию (`century: 0, decade: 1, year: 2, month: 3, day: 4, hour: 5, minute: 6, second: 7`). События более крупных масштабов выдаются первыми.
2. Протяженность события по убыванию (`(end_date - start_date) DESC`, для точечных событий длительность принимается равной 0).
3. Псевдослучайный хэш Кнута по первичному ключу для равномерного и детерминированного отбора событий одинакового ранга и длительности при усечении: `((id * 2654435761) % 4294967296) ASC`.
4. Идентификатор события `id ASC` для абсолютной стабильности результирующего курсора.

##### Сериализация параметров и поведение фильтра `ranks`

* Формат передачи в URL: Коллекции значений передаются стандартным протокольным способом через повторяющиеся query-ключи, например:
`GET /api/v1/events/range?from_date=0&to_date=1000&ranks=century&ranks=year&categories=science`
* Поведение на уровне HTTP-эндпоинта: Достижимы только два состояния: параметр отсутствует (значение `None`, фильтрация отключается, сервис возвращает события всех рангов) либо параметр содержит одно или несколько допустимых значений. Передача пустой строки или недопустимого литерала (например, `?ranks=invalid`) отсекается валидацией перечисления `EventRank` со статусом HTTP 422 Unprocessable Content. По HTTP пустой список передать нельзя.
* Семантика пустого списка (`ranks=[]`): Относится исключительно к прямому вызову сервисной функции `list_events_in_range` из другого серверного кода. В этом случае сервисный слой применяет оптимизацию раннего возврата и возвращает пустой список `[]` без обращения к базе данных. На уровне CRUD пустой список транслируется в заведомо ложное SQL-условие (`1 = 0`).

#### 2. Получение события по первичному ключу (`GET /api/v1/events/{event_id}`)

Эндпоинт возвращает полную детальную информацию о конкретном историческом событии по его первичному ключу `id`.

##### Архитектурная политика публичной видимости

Прямой запрос по первичному ключу требует подтвержденного статуса модерации (`status = 'approved'`). При обращении к немодерированному событию (со статусом `pending` или `rejected`), а также к отсутствующему первичному ключу, сервер возвращает статус HTTP 404 Not Found со стандартизированным телом:

```json
{
  "detail": "Историческое событие с ID {event_id} не найдено"
}

```

Возврат статуса 404 вместо 403 или 200 полностью исключает раскрытие информации о существовании черновых или отклоненных записей внешним клиентам (защита от сканирования идентификаторов / ID Enumeration Attack).

#### 3. Получение списка дочерних событий (`GET /api/v1/events/{event_id}/children`)

Эндпоинт возвращает структурированную страницу подтвержденных дочерних событий, привязанных к одобренному родительскому событию через внешний ключ `parent_id`.

##### Параметры запроса

| Параметр | Тип данных | Расположение | Обязательный | По умолчанию | Описание и валидационные ограничения |
| --- | --- | --- | --- | --- | --- |
| `event_id` | `integer (BIGINT)` | Path | Да | — | Идентификатор родительского исторического события (допускает любые допустимые целочисленные первичные ключи). |
| `skip` | `integer` | Query | Нет | `0` | Смещение пагинации (`ge = 0`). |
| `limit` | `integer` | Query | Нет | `100` | Максимальный размер выборки дочерних событий (`ge = 1`, `le = 500`). |

##### Схема ответа и сортировка

* Возвращаемая модель: `EventChildrenPage`. Содержит массив элементов `items` (`list[EventResponse]`), общий счетчик дочерних записей в базе данных `total`, а также эхо-параметры пагинации `skip` и `limit`.
* Гарантия упорядочивания: записи сортируются в строгом хронологическом порядке по возрастанию даты начала `start_date.asc()` и эффективной даты окончания `end_date_effective.asc()`.
* Фильтрация статуса: выдача включает исключительно подтвержденные дочерние записи (`status = 'approved'`).

##### Коды ответов сервера

* 200 OK: успешная выборка страницы дочерних событий (поле `items` может быть пустым списком `[]`, если у подтвержденного родителя нет подтвержденных потомков).
* 404 Not Found: родительское событие с указанным ID отсутствует в базе данных либо находится в статусе `pending` или `rejected` (предотвращает раскрытие структуры скрытых или неодобренных веток дерева).
* 422 Unprocessable Content: ошибка валидации параметров (нечисловой `event_id`, отрицательное смещение `skip < 0`, превышение верхнего лимита `limit > 500` или `limit < 1`).

### Клиентский контур данных и модель кэширования

Клиентская часть приложения реализует реактивную двухконтурную архитектуру: математическая модель камеры синхронно управляет делениями сетки, а изолированное хранилище `eventStore.js` асинхронно буферизирует маркеры событий.

#### Ключевые архитектурные принципы контура данных

1. Модель одного загруженного окна (Single Loaded Window):
Хранилище `eventStore.js` кэширует в оперативной памяти ровно один непрерывный интервал `[from_date, to_date]` и нормализованный строковый ключ формы запроса `ranks:...|categories:...`. Если при перемещении камеры требуемое видимое окно полностью укладывается внутрь загруженного интервала, а состав рангов и категорий не изменился, сетевой запрос не выполняется, и данные мгновенно отображаются из кэша.
2. Множитель упреждения (Prefetch Multiplier):
Константа `DEFAULT_PREFETCH_MULTIPLIER = 3` расширяет запрашиваемый интервал втрое относительно видимой ширины экрана с центрированием на видимом отрезке. Нижняя граница `from_date` округляется строго вниз (`Math.floor`), а верхняя `to_date` — строго вверх (`Math.ceil`), что устраняет риск ошибки валидации FastAPI 422 при вещественных координатах камеры. Границы окна жестко ограничиваются системными пределами `TIMELINE_MIN_TIMESTAMP` и `TIMELINE_MAX_TIMESTAMP`.
3. Подавление частоты запросов (Debounce):
Задержка `DEFAULT_DEBOUNCE_MS = 250 мс` предотвращает множественные сетевые обращения при непрерывном интерактивном перемещении холста мышью или жестами. Таймер перезапускается при каждом смещении камеры, отправляя HTTP-запрос только после стабилизации положения.
4. Определение усечения выдачи и регистрация полного окна:
Для исключения скрытой потери данных клиент запрашивает лимит `softLimit + 1` (501 запись при стандартном лимите 500). При получении количества записей, превышающего мягкий лимит, хранилище устанавливает признак усечения `isTruncated = true`, отсекает лишний элемент и регистрирует полное запрошенное упреждающее окно `loadedWindow = windowToLoad` без сужения по дате последнего события. Одновременно фиксируется масштаб запроса `loadedZoomIndex`. Повторный запрос данных при усечении инициируется только при приближении масштаба (zoom in) на величину `loadedZoomIndex - currentZoomIndex >= TRUNCATED_REFETCH_ZOOM_INDEX_DELTA` (1.0). Любое панорамирование внутри зарегистрированного окна обслуживается строго из локального кэша, предотвращая лавины повторных запросов.
5. Защита от гонки ответов (Race Conditions) и освобождение памяти:
Перед отправкой каждого нового сетевого запроса активный запрос прерывается через `AbortController.abort()`. Дополнительно ведется учет монотонного порядкового номера `requestId`: запоздалые ответы от ранее отправленных запросов гарантированно отбрасываются. При размонтировании экрана метод `destroy()` контроллера останавливает таймеры, прерывает сетевой контур и блокирует вызовы колбэков, предотвращая утечки памяти.
6. Экспоненциальная задержка при сетевых отказах (Exponential Backoff):
Задержка планирования удваивается при каждом последовательном сбое вплоть до восьмикратного базового интервала `debounceMs * Math.pow(2, Math.min(consecutiveFailures, 3))` (до 2000 мс при базовом дебаунсе 250 мс). После первого успешного ответа задержка возвращается к базовой. Ранее загруженные события при отказе сети сохраняются на экране для обеспечения непрерывности отображения.

## 4. Архитектура клиентской компоновки и интерактивного взаимодействия

Клиентское ядро таймлайна строится на строгом разделении ответственности между одномерной горизонтальной проекцией (`markers.js`), вертикальным распределением полос (`layout.js`), геометрической детекцией курсора (`hitTest.js`), реактивным состоянием выбора (`selection.js`), адаптивной фокусировкой (`focus.js`), моделью слоев (`layers.js`), реестром категорий (`categories.js`) и графическим конвейером (`renderer.js`).

### 1. Вертикальная геометрия и отсчет от оси времени

* Базовая линия полосы дорожек `baseY` отсчитывается вверх от горизонтальной оси времени: `baseY = axisY - MARKER_OFFSET_FROM_AXIS`, где `axisY = Math.floor(heightPx * AXIS_POSITION_RATIO)`.
* Дорожка с индексом 0 располагается вплотную над осью времени, а последующие дорожки поднимаются вверх к верхнему отступу `MARKER_LANES_TOP_PADDING_PX = 24px`.
* Доступная высота `availableHeight` динамически нарезается на дорожки с межстрочным зазором `LANE_VERTICAL_GAP_PX = 4px`. Высота дорожки `laneHeight` вычисляется функцией `calculateLaneHeight` на основе фактически занятых дорожек в пределах от `LANE_MIN_HEIGHT_PX = 12px` до `LANE_MAX_HEIGHT_PX = 22px`.
* Базовая высота холста составляет `TIMELINE_CANVAS_HEIGHT_PX = 440px`.

### 2. Жадное распределение по дорожкам и стабилизация (Stickiness)

* Маркеры предварительно упорядочиваются по шкале приоритета `createMarkerPriorityComparator`. Приоритет ранга детализации остается абсолютным первичным ключом, а в пределах одного ранга преимущество отдается маркерам более приоритетного слоя категорий.
* Для исключения скачков дорожек между кадрами панорамирования контроллер передает в `computeTimelineLayout` карту `previousLaneAssignments`. Если сохраненная за событием дорожка свободна, маркер закрепляется на ней. В противном случае алгоритм жадно находит первую свободную дорожку снизу вверх.
* Для предотвращения визуального слияния маркеров габариты расширяются на горизонтальный зазор безопасности `LANE_HORIZONTAL_GAP_PX = 6px`.

### 3. Резервирование дорожки переполнения

При наличии двух и более доступных дорожек (`maxLanes >= 2`) верхняя дорожка с индексом `maxLanes - 1` резервируется исключительно под маркеры переполнения. Основные маркеры событий распределяются по дорожкам от 0 до `maxLanes - 2`. Это гарантирует отсутствие взаимных наложений между маркерами событий и бейджами переполнения.

### 4. Плашки переполнения (Overflow Badges)

Вытесненные события, которым не хватило места на основных дорожках, кластеризуются по экранной координате с шагом ширины плашки `OVERFLOW_BADGE_WIDTH_PX = 28px` плюс зазор безопасности. На зарезервированной верхней дорожке формируются маркеры переполнения с текстом `+N`. Клик по маркеру переполнения вызывает центрированное приближение виртуальной камеры (`zoomViewport` с шагом `-ZOOM_STEP_PER_WHEEL_NOTCH * 2`), раскрывая подробности.
Координата `screenX` дескриптора переполнения обозначает строго его левую границу (аналогично интервальным маркерам), заливка подложки выполняется от `screenX`, текстовый счетчик центрируется в точке `screenX + widthPx / 2`, а область детекции хит-теста охватывает интервал от `screenX` до `screenX + widthPx` с допуском `HIT_TEST_TOLERANCE_PX`.

### 5. Серверная агрегация и бейджи скрытых потомков

* Подсчет скрытых потомков перенесен на уровень СУБД (поле `collapsed_children_count`). Все пришедшие с сервера события компонуются на дорожках независимо. Счетчик `collapsed_children_count` вычисляется сервером на уровне базы данных для любого подтвержденного родителя независимо от тематических категорий потомков; на клиенте круговой бейдж агрегата размещается на маркере родителя и наследует его переменную темы `themeVariable`, обеспечивая согласованную цветовую индикацию и прозрачность слоя родительского события.
* Круговой бейдж агрегации радиусом `AGGREGATE_BADGE_RADIUS_PX = 7px` формируется при `collapsed_children_count >= MIN_CHILDREN_FOR_AGGREGATE` (1).
* Если видимая часть полосы интервального события на экране шире диаметра бейджа с запасом, бейдж позиционируется внутри полосы у правого края. Если полоса слишком узкая либо маркер является точечным, бейдж выносится наружу вправо с отступом `AGGREGATE_BADGE_EDGE_PADDING_PX = 2px`.
* Габариты маркера с бейджем учитываются при расчете коллизий через `computeMarkerLayoutBounds`.

### 6. Единый расчет пространственной компоновки

Раскладка дорожек вычисляется ровно один раз в функции `updateCurrentLayout` контроллера и сохраняется в переменной `currentLayout`. Готовый слепок передается в пассивный рендерер `renderer.requestRender(state, currentLayout)` и функцию хит-теста `resolveCursorTarget`, исключая дублирование тяжелых геометрических вычислений в анимационном цикле.

### 7. Боковая панель детализации (Detail Panel) и адаптивная фокусировка камеры

* Компонент `createDetailPanel` монтируется в DOM-дерево один раз при инициализации экрана `home.js`.
* Защита от XSS: свойство `innerHTML` категорически не используется, текстовые поля заполняются строго через `textContent` или создание текстовых узлов `document.createTextNode`.
* Форматирование дат карточки и дочерних событий выполняется функцией `formatEventDateRange(start_date, end_date, rank)` с точностью, соответствующей доменному рангу детализации.
* Категория события визуализируется бейджем с русскоязычным названием и цветной левой полосой шириной 3px через CSS-переменную `--badge-color`. В списке дочерних событий каждый элемент снабжен миниатюрным цветовым образцом направления `.timeline-detail-child-swatch`.
* При частичной выборке потомков выводится информационный блок с классом `.timeline-detail-children-count`: «Показано N из M».
* Клик по дочернему событию вызывает метод `timelineController.focusEvent(child)`. Модуль `focus.js` центрирует виртуальную камеру на временных координатах потомка и с помощью пошагового спуска `findZoomIndexForRank` подбирает минимально необходимый масштаб детализации для гарантированной видимости ранга выбранного события.

### 9. Модель и панель управления слоями (Layers Engine)

* Структура состояния слоев `{ version: 1, order, visible, opacity }` полностью неизменяема (глубокая заморозка через `Object.freeze`). Функция `normalizeLayerState` восстанавливает корректное состояние при передаче поврежденных данных, дубликатов или устаревших схем, отсекая неизвестные идентификаторы и дополняя недостающие категории из `CATEGORY_IDS`.
* Семантика порядка категорий и закрепление дорожек: в массиве `order` (сверху вниз) нулевой элемент имеет наивысший приоритет, размещается на дорожках ближе всего к оси времени и вытесняется на дорожку переполнения последним при дефиците емкости. В массиве рендерера `drawOrder` порядок инвертируется (снизу вверх с запасным слоем первым), благодаря чему приоритетный слой рисуется поверх остальных в графическом конвейере Canvas. При изменении порядка категорий план переходов `planLayerStateTransition` выставляет разовый флаг сброса закрепления `resetLaneAssignments = true`, заставляя компоновщик пересчитать дорожки с чистого листа и переместить поднятый слой вплотную к оси времени. При изменении только видимости слоев закрепление дорожек сохраняется (`resetLaneAssignments = false`), исключая скачки строк у оставшихся видимых событий.
* Порог непрозрачности и контрастность: минимальный коэффициент непрозрачности составляет `LAYER_OPACITY_MIN = 0.4` (40%). Результаты инструментальных замеров контрастности к темному фону `#121214` показывают, что при коэффициенте 0.4 контраст составляет 1.5–2.0:1 (тогда как при прежнем значении 0.2 контраст составлял всего 1.18–1.33:1). Данный порог исключает возникновение визуально невидимых, но интерактивно кликабельных маркеров в контуре хит-тестирования. Шаг `LAYER_OPACITY_STEP = 0.1` используется не только в элементах интерфейса, но и в качестве квантователя дискретизации в функции `snapLayerOpacity` для устранения дробного шума чисел с плавающей точкой стандарта IEEE 754.
* Изоляция Web Storage и безопасность среды: обращение к свойству `globalThis.localStorage` вынесено в изолированную внутреннюю функцию `resolveDefaultStorage()`, предотвращая сбой приложения с ошибкой `SecurityError` при блокировке локальных данных сайта в приватном режиме браузера. Функции `loadLayerState(storage)` и `saveLayerState(state, storage)` не содержат параметров по умолчанию, строго валидируют наличие методов `getItem`/`setItem` и возвращают безопасный fallback при передаче невалидных объектов или `null`.
* Логика фильтрации: функции `isCategoryFilterActive` (проверяет наличие скрытых слоев), `getCategoryRequest` (при скрытии всех слоев сетевые запросы прекращаются; при частичном скрытии запрашиваются только видимые категории) и `filterEventsByLayers` (клиентская фильтрация событий, при которой события с неизвестной категорией пропускаются только при отсутствии активного фильтра).
* Сохранение состояния: состояние слоев сериализуется в локальное хранилище браузера `localStorage` по ключу `history_timeline.layers` с целочисленной версией схемы `LAYER_STATE_VERSION = 1`.
* Архитектура компонента `layerPanel.js`: построение интерфейса без использования `innerHTML` (все узлы создаются через `createElement`, а текст передается через `textContent`), динамические границы и шаг ползунка непрозрачности на базе констант `LAYER_OPACITY_MIN`, `LAYER_OPACITY_MAX`, `LAYER_OPACITY_STEP`, атрибут доступности `aria-label` у кнопки «Только», быстрые кнопки-чипы фильтрации с индикатором `aria-pressed`, сворачиваемый блок настроек `details.layer-manager`, централизованное делегирование событий и автоматическое сохранение фокуса клавиатуры при перемещении слоев.
* Индикаторы панели инструментов тулбара: разделение счетчиков событий и категорий исключает составную форму «N из M». Индикатор «Событий:» отображает строго одиночное число отфильтрованных видимых событий. Индикатор «Направления:» (`div#timeline-directions-wrapper` со стилем `.timeline-directions-info`) скрыт по умолчанию (`hidden`) и отображает «k из n» по данным `countVisibleLayers` только при активности фильтра (`isCategoryFilterActive`). При скрытии всех категорий (`getCategoryRequest().shouldRequest === false`) индикатор статуса выводит «Все направления скрыты» цветом `var(--text-secondary)`, предупреждение об усечении скрывается, а сетевые запросы к API полностью блокируются.

### 10. Соглашение шкалы в UTC, системные часы и маркер текущего момента

* Архитектурное соглашение единого времени: временная координатная сетка таймлайна, календарное разложение секунд Unix и положение вертикальной линии маркера «Сейчас» рассчитываются строго в шкале UTC.
* Назначение компонента `clock.js`: вывод локального гражданского времени пользователя со смещением относительно UTC (`formatUtcOffset`), формирование атрибута `datetime` элемента `time` в стандарте ISO 8601 и всплывающей подсказки `title` с пояснением времени в UTC.
* Тактовая синхронизация: каждый следующий тик часов планируется строго на границу следующей секунды с добавлением запаса `CLOCK_TICK_SAFETY_DELAY_MS = 20` мс, что исключает повторное срабатывание в пределах одной секунды из-за погрешностей системного таймера.
* Энергосбережение: интеграция с Page Visibility API останавливает планирование таймера при переходе вкладки в фоновый режим (`visibilityState === 'hidden'`) и немедленно актуализирует отображение времени и маркер при возврате фокуса.
* Оптимизация обновления маркера «Сейчас»: вызов `timelineController.refreshNowMarker()` запрашивает перерисовку кадра Canvas по секундным тикам только в том случае, если текущий физический масштаб не превышает `NOW_MARKER_REFRESH_MAX_SPP = 60` с/пкс (1 минута на пиксель) и маркер находится в видимой области экрана с запасом 20 пикселей. На обзорных масштабах секундное смещение маркера составляет доли пикселя, и холостые перерисовки холста блокируются.

### 11. Безопасное подмножество разметки Markdown

Архитектурный принцип полного отказа от innerHTML: клиентский рендерер не генерирует HTML-строки и полностью исключает использование сторонних библиотек (marked, markdown-it, DOMPurify). Собственный синтаксический анализатор parser.js строит промежуточное абстрактное синтаксическое дерево (AST), из которого DOM-узлы создаются программно через вызовы document.createElement, document.createTextNode и textContent в renderer.js.

Поддерживаемые блочные элементы разметки:

* Заголовки (Headings): поддерживаются заголовки с понижением уровней. Уровни h1 и h2 понижаются до уровня 3 для сохранения семантической структуры SPA-приложения; уровни h3, h4 и h5 сохраняются без изменений; уровень h6 понижается до уровня 5.
* Блоки исходного кода (Fenced Code Blocks): блоки текста, ограниченные тройными обратными кавычками с опциональным указанием идентификатора языка программирования (например, python, javascript). Генерируют элементы pre > code с присвоением класса language-{lang} и буквальным выводом текста.
* Блоки цитат (Blockquotes): многострочные фрагменты с префиксом >. Глубина рекурсивной вложенности жестко ограничена порогом MAX_NESTING_DEPTH = 4. При превышении лимита вложенные структуры сворачиваются в линейные параграфы.
* Маркированные списки (Unordered Lists): элементы с маркерами дефиса (-), звездочки (*) или плюса (+). Маркеры списка добавляются строго к непустым строкам.
* Нумерованные списки (Ordered Lists): последовательности пунктов с сохранением исходного стартового номера (атрибут start тега ol).
* Тематические разделители (Thematic Breaks): горизонтальные линии из трех и более дефисов (---), звездочек (***) или подчеркиваний (___).

Поддерживаемые строчные элементы (Inline):

* Полужирное начертание текста: маркеры двойных звездочек или двойных подчеркиваний. Генерируют тег strong.
* Курсивное начертание текста: маркеры одиночной звездочки или одиночного подчеркивания. Генерируют тег em.
* Зачеркнутый текст: маркеры двойных тильд (~~текст~~). Генерируют тег del.
* Инлайн-код: фрагменты текста внутри одиночных обратных кавычек. Разметка внутри инлайн-кода не интерпретируется. Генерируют тег code.
* Внешние гиперссылки: формат [текст](https://www.google.com/search?q=url) или [текст](https://www.google.com/search?q=url). Алгоритм поддерживает сбалансированные круглые скобки внутри адреса URL с учетом экранирования (например, для статей Википедии со скобками в пути и функций javascript:(alert)(1)). Запрещено создание вложенных ссылок: ссылка не может содержать другую ссылку в соответствии со спецификацией CommonMark. Для серий несбалансированных квадратных скобок обеспечивается линейная асимптотическая скорость сканирования O(N) через кэширование поиска закрывающего символа.

Архитектурный запрет исполнения сырого HTML:

* Любые HTML-теги экранируются и выводятся как буквальный текст без декодирования.
* Попытки внедрения исполняемых скриптов script, фреймов iframe, объектов object и тегов с обработчиками событий onerror, onload, onclick полностью нейтрализуются без создания исполняемых узлов DOM.
* Счетчик создаваемых узлов ограничен лимитом MAX_RENDER_NODES = 2000 узлов. При превышении порога вывод усекается с добавлением информационного сервисного уведомления.

### 12. Политика безопасности внешних гиперссылок (linkPolicy)

Модуль linkPolicy.js реализует строгую валидацию, санитизацию и генерацию безопасных атрибутов гиперссылок на базе стандарта WHATWG URL.

Разрешенные схемы сетевых протоколов:

* Разрешены строго сетевые протоколы http: и https:.
* Поддерживаются ссылки с нестандартными сетевыми портами для внешних ресурсов, интернационализированные доменные имена IDN и адреса в кодировке Punycode.

Правила отсечения недопустимых ссылок:

* Блокировка потенциально опасных псевдопротоколов: javascript:, data:, vbscript:, file:, blob:.
* Блокировка относительных ссылок (/path, ../config.json, #anchor) и протокольно-относительных адресов (//evil.com).
* Блокировка ссылок с внедренными учетными данными пользователя (userinfo: user:pass@host или admin@host) для предотвращения фишинговых атак.
* Блокировка адресов со скрытыми пробелами, символами табуляции, переносами строк и нулевыми байтами \0 в схеме протокола.

Защитные атрибуты генерируемых тегов a:

* target="_blank" для обязательного открытия внешних документов в новой вкладке браузера.
* rel="noopener noreferrer nofollow ugc" для изоляции контекста window.opener, предотвращения утечки реферера и разметки пользовательского контента.
* При обнаружении недопустимой или опасной схемы тег a не создается; содержимое ссылки нейтрализуется в безопасный элемент span с классом markdown-unsafe-link.

### 13. Реестр доверенных медиа-провайдеров и спецификация встраивания

Серверный сервис media_parser.py и клиентский реестр providers.js обеспечивают эшелонированную защиту при валидации и встраивании мультимедийных ресурсов.

Спецификация для YouTube:

* Разрешенные домены: youtube.com, www.youtube.com, m.youtube.com, youtu.be, youtube-nocookie.com, www.youtube-nocookie.com.
* Канонический адрес встраивания: https://www.youtube-nocookie.com/embed/{video_id}.
* Идентификатор контента: строго 11 ASCII-символов из набора ^[a-zA-Z0-9_-]{11}$.
* Поддерживаемые форматы URL: стандартный /watch?v={id}, короткие ссылки youtu.be/{id}, встраивание /embed/{id}, вертикальные ролики /shorts/{id}.
* Атрибуты песочницы: sandbox="allow-scripts allow-same-origin allow-presentation".
* Атрибуты разрешений: allow="accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share; fullscreen".

Спецификация для Rutube:

* Разрешенные домены: rutube.ru, www.rutube.ru.
* Канонический адрес встраивания: https://rutube.ru/play/embed/{video_id}.
* Идентификатор контента: ровно 32 шестнадцатеричных символа в нижнем регистре ^[a-f0-9]{32}$.
* Поддерживаемые форматы URL: /video/{id}/ и /play/embed/{id}.
* Атрибуты песочницы: sandbox="allow-scripts allow-same-origin allow-presentation".
* Атрибуты разрешений: allow="clipboard-write; picture-in-picture; fullscreen".

Спецификация для VK Video:

* Разрешенные домены: vk.com, www.vk.com, vkvideo.ru, www.vkvideo.ru.
* Канонический адрес встраивания: https://vk.com/video_ext.php?oid={oid}&id={id} (с добавлением &hash={hash} при наличии ключа).
* Идентификаторы: параметр oid (целое число сообщества или пользователя, допускается отрицательное) ^-?\d+$, параметр id (положительное целое число видеозаписи) ^\d+$, опциональный параметр hash ^[a-zA-Z0-9]+$.
* Поддерживаемые форматы URL: /video{oid}_{id} и плеер-виджет /video_ext.php.
* Атрибуты песочницы: sandbox="allow-scripts allow-same-origin allow-presentation".
* Атрибуты разрешений: allow="autoplay; encrypted-media; fullscreen; picture-in-picture; screen-wake-lock".

Спецификация для Яндекс.Музыки:

* Разрешенные домены: music.yandex.ru, www.music.yandex.ru.
* Плеер для трека: https://music.yandex.ru/iframe/#track/{track_id}/{album_id} при формате /album/{album_id}/track/{track_id}.
* Плеер для альбома: https://music.yandex.ru/iframe/#album/{album_id} при формате /album/{album_id}.
* Идентификаторы: параметры track_id и album_id обязаны состоять строго из цифр ^\d+$. Классифицируется как тип audio.
* Атрибуты песочницы: sandbox="allow-scripts allow-same-origin allow-presentation".
* Атрибуты разрешений: allow="clipboard-write".

Спецификация для прямых аудиофайлов (direct):

* Протокол: строго защищенный https:.
* Разрешенные расширения пути: .mp3, .ogg, .m4a, .wav, .opus (нечувствительно к регистру).
* Запрет: адреса, где расширение передается только в параметрах запроса (?file=test.mp3), а также исполняемые и стриминговые форматы (.m3u8, .mpd).
* Встраивание: нативный тег audio с атрибутами controls и preload="none".

Защита клиентского встраивания:

* Отложенная загрузка: интерактивный iframe создается только после явного клика пользователя по кнопке воспроизведения на фасаде карточки (компонент mediaEmbed.js).
* Защита от перекрестной подмены: клиент повторно валидирует соответствие хоста и провайдера через validateEmbedUrl перед генерацией iframe.
* Запрет нестандартных портов: сетевые адреса с явно указанными портами (например, :8443, :8080) отклоняются.
* Безопасность песочницы: токены allow-top-navigation и allow-top-navigation-by-user-activation категорически исключены из атрибутов sandbox.

### 14. Политика защиты контента (Content Security Policy)

Промежуточный слой SecurityHeadersMiddleware в app/middleware/security_headers.py внедряет заголовки безопасности HTTP и динамическую политику CSP ко всем ответам сервера.

Директивы Content Security Policy:

* default-src 'self' — запрет загрузки любых ресурсов с неавторизованных внешних источников.
* script-src 'self' — исполнение скриптов строго из собственного домена приложения без eval.
* style-src 'self' 'unsafe-inline' — загрузка стилевых таблиц приложения и встроенных стилей интерфейса.
* img-src 'self' https: data: — загрузка графических материалов по защищенному протоколу https и data-uri.
* media-src https: 'self' — воспроизведение прямых аудиопотоков по протоколу https.
* object-src 'none' — полный запрет устаревших плагинов Flash, Java, ActiveX.
* base-uri 'self' — ограничение корневого адреса документа собственным доменом.
* frame-ancestors 'none' — полный запрет встраивания интерфейса приложения во внешние фреймы (защита от кликджекинга, дублирует X-Frame-Options: DENY).
* frame-src 'self' https://{host} https://*.{host} — динамическое наполнение источниками встраивания на основе доверенного белого списка settings.embed_allowed_hosts.

Изоляция интерактивной документации OpenAPI:

* Маршруты /docs (Swagger UI), /redoc (ReDoc) и /openapi.json исключены из наложения жесткой политики CSP. Это гарантирует работоспособность внешних CDN-скриптов и стилей Swagger UI без ущерба для безопасности основных продуктовых эндпоинтов и клиентского SPA.

Соответствие клиентского приложения правилу no-inline-style:

* В клиентских представлениях и компонентах устранены прямые атрибуты style="..." в разметке и коде, управление внешним видом переведено на CSS-классы и переменные палитры.

### 15. Архитектурный регламент: Как добавить нового медиа-провайдера

Для подключения нового внешнего медиа-сервиса в систему требуется выполнить регламентированные шаги в серверном и клиентском контурах проекта:

Серверные шаги (Backend):

1. Добавление идентификатора: в файле app/services/media_parser.py добавьте новый строковый элемент в перечисление MediaProvider (StrEnum).
2. Белый список доменов: в app/services/media_parser.py добавьте кортеж доменных имен нового сервиса в словарь ALLOWED_HOSTS_BY_PROVIDER.
3. Разбор и валидация адреса: в app/services/media_parser.py реализуйте функцию разбора *parse*{provider}(parsed, raw_url) со строгой проверкой регулярными выражениями путей, параметров запроса и идентификатора контента, формирующую канонический embed_url. Подключите вызов функции в parse_media_url.
4. Конфигурация заголовков CSP: в app/core/config/config.py добавьте канонический домен сервиса в список по умолчанию settings.embed_allowed_hosts, чтобы он автоматически попал в директиву frame-src.
5. Тестовое покрытие: в tests/unit/test_media_parser.py добавьте тесты разбора корректных URL, отсечения некорректных ID и неизвестных путей; в tests/unit/test_schemas.py проверьте валидацию Pydantic-модели MediaItem.

Клиентские шаги (Frontend):

1. Регистрация параметров встраивания: в файле frontend/js/media/providers.js добавьте конфигурацию нового сервиса в объект PROVIDER_EMBED_CONFIGS: список allowedHosts, префикс пути pathPrefix, обязательные токены sandbox и строку разрешений allow.
2. Валидация адреса: в frontend/js/media/providers.js убедитесь, что функция validateEmbedUrl корректно валидирует протокол, домен, отсутствие портов и префикс пути для нового провайдера.
3. Генерация плеера: в frontend/js/media/mediaEmbed.js при необходимости добавьте специфичную разметку карточки предпросмотра или параметров контейнера.
4. Предвалидация в формах: в frontend/js/views/create_event.js добавьте проверку нового провайдера в функцию detectMediaProvider и обработчик подсказок validateMediaUrlClient.
5. Тестовое покрытие: в tests/js/mediaProviders.test.js добавьте тесты валидации хоста, проверки embed_url, отклонения перекрестной подмены и получения атрибутов песочницы; в tests/js/mediaEmbed.dom.test.js проверьте генерацию карточки и монтирование iframe.

ruff check .

## 6. Тестирование и метрики покрытия

Запуск полного набора серверных тестов с консольной сводкой:

```bash
pytest

```

*(Лог выполнения теста, детали миграций и сводка покрытия автоматически дублируются без ANSI-кодов в файл `project_info/pytest_last_run.txt`).*

pytest --cov-report=html

htmlcov/index.html

### Клиентский контур (JavaScript / Vitest)

Обеспечивает модульное тестирование математического ядра таймлайна в изолированной среде Node.js и виртуальном DOM-окружении happy-dom. Валидирует сетевой слой (`api.test.js`), календарную арифметику (`calendar.test.js`), реестр категорий и контраст WCAG (`categories.test.js`), модель слоев и Web Storage (`layers.test.js`), компонент часов и Page Visibility API (`clock.test.js`), DOM-компонент панели слоев (`layerPanel.dom.test.js`), масштабирование (`scale.test.js`), модель камеры (`viewport.test.js`), координатную сетку (`ticks.test.js`), форматирование дат (`format.test.js`), маппинг рангов (`rankMapping.test.js`), расчет окон загрузки (`loadWindow.test.js`), геометрию маркеров (`markers.test.js`), хранилище событий (`eventStore.test.js`), алгоритмы компоновки дорожек (`layout.test.js`), геометрический хит-тест (`hitTest.test.js`), реактивное хранилище выбора (`selection.test.js`), фокусировку камеры (`focus.test.js`), логику контроллера (`controller.test.js`), функции форматирования текста редактора (`editorActions.test.js`), синтаксический анализ Markdown (`markdownParser.test.js`), безопасный рендерер AST (`markdownRenderer.test.js`), политику ссылок (`linkPolicy.test.js`), реестр медиа-провайдеров (`mediaProviders.test.js`), компонент фасадов встраивания (`mediaEmbed.dom.test.js`), панель деталей (`detailPanel.dom.test.js`) и представление создания события (`createEvent.dom.test.js`).

Запуск всех модульных тестов клиентского ядра:

```bash
npm test

```

Запуск тестов напрямую через Vitest в режиме разового прогона:

```bash
npx vitest run

```

### Архитектурная изоляция контуров тестирования

Контуры Python и JavaScript полностью изолированы:

* pytest исполняет только тесты бэкенда из каталогов `tests/unit` и `tests/integration`, не затрагивая JavaScript-файлы.
* Vitest исполняет тесты математического ядра и DOM-компонентов из каталога `tests/js`, не требуя запуска интерпретатора Python или подключения к базе данных.
* В конвейере CI (`.github/workflows/ci.yml`) проверка ESLint (`npm run lint`) и тесты Vitest (`npm test`) запускаются на раннем этапе lint сразу после установки Node.js, предотвращая запуск тяжелых сервисных контейнеров базы данных при ошибках в клиентской логике. Серверные тесты исполняются изолированно в задании test.
