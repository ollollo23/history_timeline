# Сводный отчет сверки дефектов аудита и задач спринта стабилизации

## 1. Контекст и цели проведения аудита

Настоящий сводный отчет фиксирует результаты сверки обнаруженных архитектурных дефектов и уязвимостей исходной кодовой базы платформы History Timeline API с реализованными решениями в рамках спринта стабилизации. 

Целями комплекса стабилизационных мероприятий являлись:
- Ликвидация критических векторов атак (инъекции в медиа-полезную нагрузку, подделка статусов модерации, утечки учетных данных);
- Устранение связности между слоями представления, бизнес-логики и доступа к данным с переходом на принципы Clean Architecture;
- Внедрение паттерна Unit of Work на уровне сессии базы данных с исключением ручного управления транзакциями в CRUD-слое;
- Верификация ключевых реляционных инвариантов PostgreSQL 18 (7 действующих ограничений CheckConstraint, вычисляемая колонка end_date_effective, каскадное действие ON DELETE SET NULL внешнего ключа parent_id) через изолированный интеграционный контур тестов;
- Построение отказоустойчивого автоматизированного CI/CD конвейера со статическим аудитом безопасности, контролем покрытия тестами (>= 80%) и шлюзом ручного подтверждения релизов.

## 3. Аналитическое обоснование отложенных задач спринта

### 3.1. Идентификация автора события (`author_id`) и ролевая модель (RBAC)
- **Причина переноса:** Попытка внедрения поля `author_id` в рамках текущего спринта стабилизации привела бы к нарушению принципа минимальной необходимой сложности. Полноценная реализация авторства требует проектирования агрегата учетных записей (`User`), сущностей ролей и прав доступа, инфраструктуры хэширования паролей (Argon2id), криптографической верификации JWT-токенов и внедрения глобального контекста авторизации `Depends(get_current_user)`.
- **Архитектурное решение:** В текущей схеме событий создание записей выполняется через открытый публичный шлюз с обязательной фиксацией статуса `status = "pending"`. Доменная модель событий подготовлена к расширению внешним ключом `author_id` без разрушения обратной совместимости после реализации сервиса пользователей в спринте Auth/RBAC.

### 3.2. Санитизация Markdown-разметки текстовых описаний
- **Причина переноса:** Архитектура REST API оперирует сырыми текстовыми данными в формате Markdown, выступая в роли хранилища контента. Сам по себе Markdown-текст не является исполняемым контекстом и не представляет угрозы внедрения межсайтового скриптинга (XSS) до момента его преобразования в HTML-структуру документа.
- **Архитектурное решение:** Санитизация разметки с использованием парсеров `nh3` или `bleach` перенесена на уровень интерфейсного представления (Frontend Rendering Pipeline). Очистка потенциально опасных тегов (`<script>`, `<iframe>`, событийных обработчиков `onload/onerror`) выполняется непосредственно перед монтированием узлов в DOM-дерево клиентского браузера.

### 3.3. Keyset-пагинация (Cursor-based Pagination) интервальной выборки
- **Причина переноса:** Замена традиционной пагинации `OFFSET / LIMIT` на курсорную пагинацию требует двустороннего изменения контракта: клиентское SPA-приложение должно хранить и передавать составной токен курсора (`start_date`, `end_date_effective`, `id`). В условиях текущего объема данных временного окна (лимит выборки зафиксирован на уровне до 5000 объектов) накладные расходы `OFFSET` нивелируются покрывающим композитным B-Tree индексом `ix_events_start_effective`.
- **Архитектурное решение:** Задача оптимизации выборки до курсорной модели перенесена в спринт масштабирования (Scale Sprint), где будет реализован протокол синхронизации бесконечного зума таймлайна с поддержкой оконных функций и потоковой передачи данных по WebSocket или SSE.

### 3.4. Экспериментальное профилирование диапазонных запросов: доказательное обоснование перехода на функциональный GiST-индекс
- **Параметры экспериментального стенда:**
  - СУБД и среда исполнения: PostgreSQL 18 на платформе Windows 11;
  - Объем испытательного датасета: 10 000 синтетических исторических событий со статусом `approved`;
  - Размер буферного пула таблицы: 371 блок (Shared Buffers);
  - Методология замеров: предварительный прогрев кэша (warm-up) и усреднение по 50 итерациям выполнения запроса `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` для каждого интервала.
- **Причина деградации B-Tree индекса:** Предикат `start_date <= to_date` обладает слабой избирательностью при поиске интервалов, перекрывающих целевое окно. Из-за этого планировщик оптимизатора PostgreSQL 18 полностью отказывается от композитного B-Tree индекса в пользу полного последовательного сканирования таблицы (`Seq Scan`). Процесс сопровождается принудительным чтением всего объема страниц (371 блок) и последующим ресурсоемким отсевом строк процессорным фильтром (`Rows Removed by Filter`) с долей отсева от 75.4% до 100.0%.
- **Фактическая ведомость контрольных замеров:**

| Стратегия и предикат | Диапазон выборки | Тип узла сканирования (Node Type) | Время выполнения (Execution Time) | Буферы Shared Hit | Отброшено фильтром | Доля отсева |

  Функциональный GiST-индекс `ix_events_int8range_gist` продемонстрировал превосходство над B-Tree:
  - Ускорение времени выполнения запросов достигает **32 раз** на точечных диапазонах (с 0.832 мс до 0.026 мс);
  - Нагрузка на буферную подсистему СУБД снижена более чем в **46 раз** (с 371 до 8 блоков при точечных запросах);
